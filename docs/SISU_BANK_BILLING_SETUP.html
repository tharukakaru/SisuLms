Step 3 — Configure the owner and secure site connection

  1. Provision the verified owner account through the existing owner setup workflow. The requested owner is danusgalagoda@gmail.com; do not create an unverified owner by changing a browser role.
  2. Use deploy/final-control-config.example.json and deploy/final-tenant-config.example.json as examples. Configure matching tenant registry IDs and canonical site hostnames.
  3. Configure one unique secret of at least 32 characters per tenant in the secret manager. The control plane uses il_tenant_signing_keys; the tenant uses il_control_plane_key. Never put secrets in frontend files, Git, screenshots or this guide.

Package changes take effect next cycle. These assignments do not automatically convert old invoices, old wallet credits or old student entitlements.

Step 4 — Confirm the pricing rule

SISU formula: monthly base + rate × distinct student/class enrolments with access overlapping the billing cycle. Two separately sold theory and paper classes count twice. Weekly meetings within one class count once. A programme covering 12 modules counts once. A long course counts every monthly cycle while access remains active. Free class access also counts as an active enrolment; the teacher's tuition charge is zero.

Example: Gold and 200 class enrolments = 15,000 + (200 × 50) = LKR 25,000. A student taking theory and paper contributes two enrolments = LKR 100, not two base fees. The code does not require the student to log in or pay again each month to be counted.

Klass's public definition uses payment plus login during the billing cycle; its public page does not establish whether enrolments in multiple classes are deduplicated. SISU's per-class rule is the user's chosen model, not a claim about Klass's internal billing. Reference pricing.

Step 5 — Test student bank transfers

  1. Create an institute-owned class and an independently owned teacher class. Confirm the owner on each; an assigned institute teacher must not become the beneficiary.
  2. Set the class access duration: Day, Week, Month, Year, Session, Course or Custom. Session/Course/Custom require an end date.
  3. Enrol a test student. Open the resulting unpaid class invoice.
  4. In Class fees, upload a test PNG/JPEG/PDF slip up to 5 MB, the matching amount, transfer date and bank reference. Proof files are private.
  5. Confirm the status is Pending and the student still cannot access protected class content.
  6. As the assigned teacher or institute admin, view the slip. Check the payment in the actual bank account before approving. Enter a verification note and correct access window. For a six-month programme, select Course and its real end date, not a one-month default.
  7. Approve the test slip. Confirm the invoice is paid, access begins/ends correctly and a second approval cannot create another payment. Reject another slip and confirm it grants no access.

Institute-owned payments belong to the institute; teacher compensation is handled by the institute. Independent class payments belong to the teacher. Approval records an external payment: it does not move money, deduct SISU fees or credit the retired payout wallet.

Step 6 — Test monthly provider invoices and locking

  1. The daily scheduler closes due provider cycles and creates an immutable package/enrolment invoice snapshot.
  2. Invoices are due exactly seven days after issue. Calendar month cycles are anchored to the provider's assignment date; partial access overlapping a cycle counts once, without proration.
  3. The provider can view the breakdown and print/save it as PDF in Plans & billing. Configure SMTP so the invoice email is delivered.
  4. The provider uploads payment proof. Status becomes Under review; this is not payment confirmation and does not unlock an overdue workspace.
  5. Super Admin checks the bank statement, opens the private proof, confirms the exact amount and records the bank reference and verification note.
  6. Confirm the workspace unlocks only when no other unpaid overdue invoice remains. Test the boundary immediately before and at the due time. Existing students are also blocked while their provider is overdue.

Test teacher/student/institute separation with direct API requests too. UI buttons alone are not authorization. Scheduled teaching hours in the report are explicitly scheduled hours, not measured Zoom/Meet attendance.

Step 7 — Request the correct HNB integration pack

Contact HNB's merchant/IPG team through the official HNB Internet Payment Gateway page. Ask for your merchant's actual integration product, sandbox, current API/SDK guide and onboarding requirements. HNB's public material describes different gateway partnerships; do not assume a protocol from an old example.

  • Hosted checkout or tokenisation flow, authentication method, supported currency and amount units.
  • Server callback signature verification, timestamp/replay rules, retry behaviour and reconciliation/status API.
  • Test credentials and test cards through the bank's approved secure channel.
  • Refund/void/chargeback rules and settlement reports.
  • Whether HNB supports separate teacher/institute merchant beneficiaries or a marketplace/sub-merchant arrangement. A single SISU merchant account must not be assumed to settle automatically to many providers.
  • Gateway/bank charges and whether settlement is gross or net. SISU does not deduct its subscription from tuition, but that does not promise the bank charges no fee.

Step 8 — Connect HNB only after receiving its documents

commercial.hnb_checkout currently rejects checkout with a clear not-configured message. New commercial invoices are blocked from the legacy PayHere/payments.lk checkout. There is no fabricated HNB callback or success response.

  1. Implement the bank's documented adapter on the server, with credentials in secret storage and exact allowlisted gateway hosts.
  2. Read the invoice, amount, LKR currency and frozen provider beneficiary from the database. Ignore browser-supplied payment amounts and beneficiary IDs.
  3. Create a durable payment attempt with a unique merchant reference before contacting the gateway.
  4. Verify HNB's callback signature using the exact documented method. Match attempt, invoice, merchant beneficiary, currency, amount and final successful status.
  5. Use a transaction and row lock to settle once. Store the gateway transaction reference and create one dated access grant with channel LMS gateway. Do not credit the old wallet or deduct the monthly SISU subscription.
  6. A browser success page must display “checking payment” until server verification completes. Reconcile ambiguous timeouts and delayed callbacks through the bank's documented status API.
  7. Run duplicate, tampered, wrong-amount, wrong-currency, wrong-beneficiary, delayed, cancelled and failed-payment tests before enabling live checkout.

Step 10 — Migrate historical records deliberately

Existing invoices are not repriced. Legacy invoices with wallet splits are not eligible for the new bank-slip workflow until reviewed and reissued by an authorised migration process. Reconcile historic settlements and import dated access grants for already-paid courses before activating the new provider account. Preserve original references and backups. There is no automatic historical financial migration in this update.

Free access grants start when a new enrolment is created. Existing free enrolments also need migration. Revocation/refund history, provider migration and large historic backfills require staging reconciliation before release.
