# Provider acceptance — all require staging

No provider below is marked accepted. Configuration presence, unit mocks, a queued email or a hosted-checkout redirect is not end-to-end acceptance. Record date, exact app/runtime version, test account, provider request/event IDs (no secrets), expected result, actual result and reviewer for each row. Use staging/sandbox recipients and accounts under your control.

Browser push integration boundary: a reviewed same-origin deployment bundle may provide `window.sisuPushAdapter.register()` returning `{device_id,token}` after user consent. Configure `il_web_push_enabled` only when that bundle/service worker and the server `il_push_adapter` are installed and accepted. The UI registers/revokes only the authenticated user's device. No Firebase key, SDK, service worker or imaginary working push service is bundled.

SMS adapter: configured dotted Python callable accepts `phone`, `message`, optional `idempotency_key`, returns `{provider_id:...}` or raises. Push adapter accepts `token`, `platform`, `body`, `idempotency_key` and returns `{provider_id:...}` or raises. Provider-specific secrets belong to the installed adapter's protected server settings. Retry semantics and webhook verification must be tested for that actual vendor.
